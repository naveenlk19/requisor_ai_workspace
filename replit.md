# Requisor - AI-Powered Project Management Platform

## Overview
Requisor is an intelligent project management platform designed for solopreneurs, freelancers, and small businesses. It integrates AI to streamline project creation, planning, and collaboration. Key capabilities include AI-assisted project generation, task analysis, workflow optimization, budget estimation, social media content generation, agile story writing, and intelligent task prioritization. The platform aims to boost productivity and provide actionable insights by combining traditional project management with advanced AI features.

## User Preferences
Preferred communication style: Simple, everyday language.
Code style: Use React with TypeScript, Tailwind CSS for styling, shadcn/ui components.
Development approach: Build comprehensive features with full functionality.
Testing approach: User manually tests features through UI interaction.

## System Architecture
Requisor is a full-stack TypeScript application built with a client-server architecture.

**Frontend**: Developed with React, TypeScript, Vite, Radix UI, Tailwind CSS, React Query, Wouter, React Hook Form, and Zod. It features a modern design with intuitive navigation and a conversational AI interface.
**Backend**: Implemented using Node.js, Express, and TypeScript, providing a RESTful API and a robust service layer.
**Database**: PostgreSQL, managed with Drizzle ORM.
**Authentication**: Utilizes OpenID Connect.
**AI Integration**: Leverages OpenAI (GPT-4o with SSE streaming, Whisper for audio transcription) and Anthropic Claude for diverse AI functionalities. CrewAI is used for content generation.
**Core Features**: Includes natural language project creation, AI-powered task breakdown, budget/quote generation, resource allocation, onboarding automation, intelligent task prioritization, and specialized content generation. It supports multi-turn conversations and context awareness.
**Build Mode**: Incorporates coding agents (Replit Agent, Claude Code, Cursor, Lovable) to generate platform-optimized implementation prompts from feature candidates, tailored to specific agents and including project context.
**Meetings & Conversations**: Manages meeting transcripts and chat exports from various sources (Slack, Zoom, Google Meet, Teams, Manual, Transcription) with AI summarization using GPT-4o.
**Brain Hub** (`/brain`): A unified, tabbed workspace that consolidates Insights (Context Brain), Meetings, Conversations, and Notes & Files (Evidence Library) into one navigation entry. Tab state is URL-synced via `?tab=insights|meetings|conversations|notes`. Legacy routes `/meetings`, `/conversations`, and `/evidence` redirect into the matching tab.

**Discovery Loop Features**:
*   **Evidence Library** (Brain → Notes & Files): A searchable repository for various data types attachable to AI conversations.
*   **Feature Prioritization & Scoring**: AI-driven (GPT-4o) and manual RICE scoring for feature candidates, displayed in a priority matrix.
*   **Streaming AI Responses**: Real-time SSE streaming for AI responses in both Plan and Build modes.
*   **Floating Prompt Suggestions**: Contextual prompt pills for guiding AI interaction.
*   **Product Usage Data Import**: Allows importing usage data for AI analysis.
*   **Feature Refinement**: Dialog for refining feature specifications with inline AI assistance.
*   **Export & Stakeholder Sharing**: Enables PDF/Markdown report export and shareable public links.
*   **Audio/Video Transcription**: `POST /api/transcribe` accepts MP3/MP4/WAV/M4A/WebM up to **2 GB**. Files ≤25 MB use a regular multipart upload; larger files use a chunked-upload flow — the client calls `POST /api/transcribe/init`, streams 20 MB chunks to `POST /api/transcribe/chunk?uploadId=&uploadToken=&index=` (each chunk safely under the Replit deployment edge proxy's ~32 MB request-body limit), and finally POSTs `{uploadId, uploadToken}` to `/api/transcribe`. The server assembles chunks at fixed byte offsets, verifies an HMAC token bound to the requesting user, and runs **AssemblyAI** with `speaker_labels: true` for diarization. Diarized output (`utterances[]` with `speaker`/`start`/`end`/`text`) is persisted to `conversations.diarized_transcript`; `participant_count` and unique speaker labels are stored alongside. A GPT-4o pass maps anonymous `Speaker A/B/…` labels to real names by combining explicit dialog cues ("Hey Naveen…") with the user's known team members (`storage.getTeamMembersByUser`) and writes the result to `conversations.speaker_map` with per-speaker confidence (only entries ≥0.6 are kept). Falls back to OpenAI Whisper for files ≤25 MB when `ASSEMBLYAI_API_KEY` is missing. Object-storage audio persistence is skipped for files >100 MB to protect heap. Cross-meeting voice fingerprinting is live via `speaker_voiceprints` (per-user registry of confirmed speakers with a 128-dim lexical/style embedding). On each new diarized transcript, `matchSpeakersToRegistry` checks anonymous labels against the registry first, GPT only fills in unmatched speakers, and every confidently-named speaker is folded back via `upsertSpeakerVoiceprintSample` so subsequent meetings auto-suggest the same person. `POST /api/conversations/:id/confirm-speaker` lets the user override or confirm a name and also learns that voiceprint immediately. The summarize route detects diarized data and prepends a `[Meeting metadata]` block (participants + talk-time %) so the AI summary explicitly lists who spoke and attributes action items to named owners. The Meetings UI shows a "View raw transcript" dialog with timestamped, color-coded speaker badges (and a copy-to-clipboard button) plus a detected-speaker badge row on every meeting card. The dialog also embeds the recording's `<audio>` player (when `conversations.audioUrl` exists) and makes every utterance row click-to-play: clicking jumps the player to that utterance's `start` (ms) and auto-pauses at `end`, with the currently-playing line highlighted via an `onTimeUpdate` cursor — providing per-line traceability back to the original audio.
*   **Meeting Integrations**: Comprehensive management and transcript fetching for Google Meet, Microsoft Teams, and Zoom.
*   **Context Brain**: A structured intelligence layer that parses raw text into categorized insights (Problems, Features, Decisions, Insights, Questions), extending the Evidence Library with `insightType` classification.
*   **Past Discoveries**: A dedicated section to list and manage feature candidates, with project filtering and manual entry capabilities.
*   **Frequency-Based Auto-Prioritization**: Tracks `mentionCount` for evidence items and feature candidates, applying a frequency boost to RICE scoring for highly mentioned topics.
*   **Recording Playback**: Audio recorded in the Meetings page is now persisted to object storage (private bucket) instead of being deleted post-Whisper; `conversations.audioUrl` + `audioMimeType` columns hold the reference; `GET /api/conversations/:id/audio` (auth + ownership) streams it for an in-list `<audio controls>` player.
*   **Bulk Transcript Upload**: `POST /api/conversations/bulk-import` accepts batches of up to 50 normalized transcript items (5 MB each), skipping auto-summarization in bulk mode. Client-side streaming pipeline (byte-budgeted ~30 MB/batch, concurrency 2) ingests thousands of files without retaining all contents in memory.
*   **Discord Integration**: OAuth bot integration for multi-user Discord browsing, channel listing, and message fetching.
*   **Gmail Integration**: Google OAuth using a **dedicated** OAuth client (`GMAIL_CLIENT_ID` / `GMAIL_CLIENT_SECRET`, scope `gmail.readonly`) — separate from the shared `GOOGLE_CLIENT_ID/SECRET` that Google Meet still uses. If the Gmail vars are missing, `/api/integrations/gmail/auth` returns 500 with a clear "Gmail integration is not configured" message and the callback redirects with `error=gmail_not_configured`. Users with Gmail already connected before the split must Disconnect and Reconnect once so a fresh refresh token is issued for the new client. The flow lets users connect their Google account from both the Integrations page and Brain → Conversations → Email tab. Both surfaces show live Connect/Disconnect controls and the connected account email; disconnect deletes the integration row so reconnects start clean. The flow is `GET /api/integrations/gmail/auth` (alias `/auth-url`) → OAuth → `/callback` (redirects back with `gmail=connected`). `GET /api/integrations/gmail/labels` lists Gmail labels for the picker. `GET /api/integrations/gmail/messages?q=&labelIds=&max=&pageToken=` returns metadata-only message rows (`{messages, nextPageToken}`) for cheap paging. `POST /api/integrations/gmail/import` accepts `{messageIds?, projectId?, query?, max?}` — picker mode imports the selected ids, otherwise the last ~25 inbox messages (skipping Promotions/Social). Each message is routed through `normalizeConversation('email', rawEml, title)` so it shares the shape of pasted/Slack/Discord conversations (stored as `source="email"`, `externalId="gmail:<msgId>"` for dedupe). Structured headers (`from/to/cc/subject/date/messageId/threadId/gmailLabels`) are persisted to `conversations.metadata.gmail`. Attachments ≤25 MB upload to the private object-storage bucket; one `conversation_attachments` row per file (id, conversationId FK CASCADE, filename, mimeType, size, objectPath) is created so files are addressable by id. `GET /api/conversations/:id/attachments` lists them and `GET /api/conversations/:id/attachments/:attachmentId/download` streams a single file (auth + ownership enforced). The import response includes per-message results `{messageId, subject, status: 'imported'|'skipped'|'failed', conversationId?, reason?}` alongside aggregate `{imported, skipped, failed, fetched}` counts. Tokens refresh automatically via the stored refresh token.
*   **Conversations Hub**: Dedicated page for ingesting team chats and emails (manual paste, Slack, Discord, Email) with unified file uploaders and backend normalizers. Summaries include AI-extracted action items routable to existing or new projects.
*   **Public Landing Page**: Serves as the public interface for unauthenticated visitors, focused on the "Context Hub" thesis. Section order: Hero → Problem → Proof → LogoStrip → Restate → Flow → Workflows → Why → Shift → FieldKit (Coming Soon — Field Capture Kit IoT recorders) → Testimonials (private-beta placeholder) → FAQ → Pricing → CTA → Footer. Primary CTA is "Start free" (→ `/auth`) with "Talk to founder →" secondary (mailto). The L1–L4 architecture detail lives on a dedicated `/architecture` page reachable from the Hero, Flow, and CTA sections.
*   **AI Token Tracking & Budget System**: Implements comprehensive token usage tracking, plan-based monthly limits, graceful degradation (GPT-4o-mini), and upgrade modals for budget management.
*   **Prompt Budget & Context Window Guard**: Central service to prevent OpenAI 400 errors by estimating and fitting prompt content within model context limits, with client-side guards and user notifications for trimmed context.
*   **Entity Graph Over Embeddings** (Task #98): A thin per-user graph layer on top of the `embeddings` table that lets retrieval answer relational questions ("who works on X?", "what blocks Y?") instead of only chunks that lexically match the query. At embed time, `server/services/entity-extractor.ts` runs gpt-4o-mini JSON-mode extraction over every successfully embedded chunk and writes typed entities (`person|company|project|feature|risk|decision|tool|topic`) and edges (`mentions|works_at|blocks|owns|attended|decided|assigned_to|said`) into new `entities` + `entity_edges` tables. Extraction is content-addressable cached via `entity_extraction_cache` keyed by `sha256(chunkText)` so re-embeds and identical text across users cost ~$0. Strict per-user scoping on entities + edges; the cache table is shared (no PII in key). The retriever (`server/services/retrieval.ts`) takes the hybrid top-K, walks 1-hop entity neighbors via `entity_edges`, and merges up to 4 "related" chunks with `metadata.via = 'entity-neighbor'` + `sharedEntity` annotation. These flow through unchanged to citations (`server/services/citations.ts` carries `via` + `sharedEntity` on each `Citation`) so the existing chip UI can show a "related" label. Telemetry columns `entities_extracted`, `edges_extracted`, `neighbors_added` were added to `ai_response_feedback` for per-question accounting. Backfill script: `scripts/backfill-entity-graph.ts`. Eval acceptance bar lives in `docs/entity-graph-eval-questions.md` (5 questions the lexical retriever can't answer today). Fail-open everywhere: extraction errors, missing `OPENAI_API_KEY`, and graph-expansion SQL errors never block embed or retrieval.
*   **Nightly Belief Consolidation** (Task #99): Promotes repeated entity-graph mentions into durable, attributed claims. A new `beliefs` table (id, userId, subjectEntityId, predicate, object, holder, weight 0..1, embedding vector(768), sourceEmbeddingIds int[], mentionCount, firstSeenAt/lastSeenAt/decayedAt, contradictionOfBeliefId self-FK, status `active|stale|contradicted`) stores one canonical claim per (subject, predicate) group. `server/services/belief-consolidator.ts` exposes `consolidateForUser(userId, sinceTimestamp)`: groups recent `entity_edges` by `(src_entity_id, predicate)`, gates on ≥3 distinct source chunks, asks gpt-4o-mini (JSON-mode) to mint `{predicate, object, weight, holder, contradicts_existing}`, dedupes against existing actives via cosine(embedding) ≥0.85 OR Levenshtein(predicate+object)/length ≤0.2, upserts/updates/marks-as-contradiction, then decays any active untouched >30 days to `stale`. Cost guard: per-user soft cap via `BELIEF_CONSOLIDATION_MAX_TOKENS_PER_USER` (default 50,000) tracked through the existing `trackTokenUsage` pipeline. `server/services/cron-scheduler.ts` ticks every 15 min and fires once-per-UTC-day when the current hour matches `BELIEF_CONSOLIDATION_HOUR_UTC` (default 9), iterating users with embedding writes in the last 7 days (`findActiveUsers`) and consolidating the prior 26-hour window. Backfill: `tsx scripts/backfill-beliefs.ts <userId>` (or `--all --days 1825`) runs the consolidator over a user's full history; safe to re-run. Retriever integration: `searchBeliefs(qVecLiteral, userId, cap=3)` in `server/services/retrieval.ts` does a pgvector cosine search over `beliefs.embedding` (cos≥0.55 filter), folds the top-3 results into the same `chunks[]` the citations pipeline reads, with `sourceType='belief'`, negative-sentinel `id` (to avoid collision with `embeddings.id` in `retrievedChunkIds[]`/faithfulness joins), and `metadata.via='belief'` + `metadata.belief = {id, holder, mentionCount, lastSeenAt, weight, status, sourceEmbeddingIds}`. `Citation` carries a new `belief` field through unchanged so the chip popover can render "claim · N sources" with an expansion affordance. `RetrievalResult` adds `beliefsAdded` alongside `neighborsAdded`/`entitiesInContext`/`edgesInContext`. The legacy `insights` table is marked `@deprecated` in `shared/schema.ts` (dual-read during transition; migration is a follow-up). Eval bar lives in `docs/belief-consolidation-eval.md`: ≥2/5 of Task #98's acceptance questions must produce a `belief:<id>`-grounded answer, with zero regressions on Task #98. Fail-open everywhere — missing `OPENAI_API_KEY`, missing `beliefs` table, embedding outage, or per-group LLM errors all degrade gracefully without blocking the day's run.
*   **MCP One-Click OAuth Connect** (Task #133): The MCP endpoint (`/api/mcp`) now supports the MCP OAuth authorization flow so Claude (claude.ai web and Claude Desktop) can connect with just the server URL — no token copy-paste. Pieces: RFC 9728 protected-resource metadata (`/.well-known/oauth-protected-resource[/api/mcp]`), RFC 8414 authorization-server metadata (`/.well-known/oauth-authorization-server[/api/mcp]`), RFC 7591 open dynamic client registration (`POST /api/oauth/register`, public clients only, exact-match redirect URIs — https, loopback http, or custom schemes), and the authorization-code + PKCE (S256 required) grant (`GET /api/oauth/authorize` → consent page → `POST /api/oauth/authorize/decision` → `POST /api/oauth/token`). All in `server/services/mcp-oauth.ts` + tables `oauth_clients` / `oauth_auth_codes` (codes stored as SHA-256 hashes, 10-min TTL, single-use). The issued access token IS a normal Personal Access Token (named "<client> (connected via OAuth)"), so `mcpTokenAuth` is unchanged, tokens appear in the Connect page list and are revocable there. Because registration is open, a consent screen is always shown (session-bound CSRF nonce); unauthenticated users bounce through `/api/login` and return via `session.oauthReturnTo` (path-only, handled in the `/api/callback` success branch). 401s from `/api/mcp` advertise `resource_metadata` in `WWW-Authenticate` for discovery, and `/api/mcp` + the token/register/metadata endpoints send permissive CORS (Bearer auth only, never cookies; the cookie'd authorize endpoint has no CORS). The Connect page leads with an "Easiest: one-click connect for Claude" card describing the URL-only setup.
*   **Unstructured.io Document Parsing** (`server/services/unstructured-parser.ts`): Hosted Unstructured.io API is used as a fallback "hard documents" parser for scanned PDFs, complex tables, multi-column layouts, and PowerPoint decks where pptx2json fails. `server/services/file-processor.ts` keeps the existing fast path (pdf-parse-new, mammoth, xlsx, pptx2json) and only routes to Unstructured when (a) PDF fast extraction returns <100 chars on a >50KB file (likely scanned, uses `hi_res` strategy with OCR), (b) PDF/DOCX text exhibits table-like layout (heuristic in `hasTableLikeLayout`), or (c) pptx2json throws. Unstructured elements are normalized to markdown (tables rendered as GFM, page breaks preserved) and `parserUsed`/page/table/image counts are surfaced via `processedFiles[]` in the `/api/ai/process-files` response. The Project Planner chat shows a violet "Unstructured · Np · N tbl" badge on staged attachment chips when richer extraction kicked in. Missing `UNSTRUCTURED_API_KEY` logs a single startup warning and gracefully falls back to fast parsers. The previous 8000-char truncation in `extractContentOnly` was replaced with chunked summarization (~6k chars/chunk, ~200 char overlap, cap 8 chunks, then merge step) so long Unstructured outputs aren't silently cut. Self-host path (Unstructured OSS container) is wire-compatible via `UNSTRUCTURED_API_URL` env override — no code changes required.
